# Design-impl

# **Streaming Lake on Pulsar + BookKeeper**

## **Executive Summary**

Streaming Lake extends Pulsar and BookKeeper to support:

* Streaming ingestion  
* Point-in-time reads  
* Predicate pushdown  
* Lakehouse-style scans  
* Point-in-time joins  
* No ETL into Iceberg/Hudi/Delta

The design introduces:

1. Topic-level date index maintained by Pulsar Broker.  
2. Page-level statistics index maintained by BookKeeper.  
3. Entry-level column statistics generated by Pulsar Broker.  
4. StreamingLakeConsumer API for predicate-based reads.  
5. Native query pruning directly against BookKeeper storage.

---

Implementation

Good catch. After thinking through scalability, I agree that **DateIndexLedger must be a dedicated ledger and not ManagedLedger metadata/ZooKeeper**. Otherwise long-retention topics would eventually hit metadata scaling issues.

Below is the revised architecture with DateIndexLedger as a first-class ledger.

# **Streaming Lake Architecture on Pulsar + BookKeeper**

## **Executive Summary**

Streaming Lake extends Pulsar and BookKeeper to support:

* Lakehouse-style scans  
* Predicate pushdown  
* Point-in-time joins  
* Time-based pruning  
* Streaming query results

without:

* Iceberg  
* Hudi  
* Delta Lake  
* ETL pipelines  
* External metadata services

The design introduces two indexing layers:

### **Pulsar Layer**

Maintains:

```
DateIndexLedger
```

used for:

```
Timestamp → Candidate Ledgers
```

### **BookKeeper Layer**

Maintains:

```
Page Index
```

used for:

```
Ledger → Candidate Pages
```

This creates a hierarchical pruning model:

```
Topic
  ↓
DateIndexLedger
  ↓
Candidate Ledgers
  ↓
BookKeeper Page Index
  ↓
Candidate Pages
  ↓
Entries
  ↓
Records
```
